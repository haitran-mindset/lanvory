# Confirmed peer pairing

On a LAN, the receiver enables incoming requests on an approved IPv4 listener. The initiator supplies the receiver's independently verified Device ID. [Bluetooth + Wi-Fi P2P](nearby.md) can carry the same pairing protocol through a helper-managed loopback bridge. The initial P2P identity probe supplies a candidate fingerprint for the pairing handshake. The scoped TCP connection uses TLS 1.3, pinned receiver identity, a client proof of possession of an Ed25519 key, and dedicated ALPN `lanvory-pair/1`. The initial client key has access only to the pairing protocol.

Both peers derive the same 128-bit confirmation value from the live TLS session with the exporter label `EXPORTER-Lanvory-Pairing-v1`. The desktop sender displays a number derived from that value. The recipient chooses the matching number from three options. Both users open **Compare verification code**, compare the full hexadecimal code over an independent trusted channel, and select **Approve pairing** on both devices. The short number is a UI check. The full code is derived locally and is not sent in the pairing messages. Each connection exchanges a one-byte approval marker and then a one-byte persistence receipt.

A daemon saves the remote fingerprint only after both approvals arrive and its network scope still permits the connection. Success requires the peer's receipt. A connection loss after both approvals can leave trust saved on one side while the initiating command reports failure. Repeating the confirmed pairing is safe. Peer keys are indexed by fingerprint, and a different key needs its own approval. The trust entry adds no resource grants.

Pending requests expire after 60 seconds, with at most eight requests and one pending request per fingerprint. Incoming requests also have a ten-second cooldown per source. A third incorrect code or a declined request cancels the session. An approval consumes the local request ID, and a new session gets a different TLS exporter value. Revoking trust also cancels pending requests for that fingerprint.

In Devices, scan Nearby and select a LAN result to prefill a resolved endpoint, or enter the endpoint manually. For LAN pairing, copy the receiving device's Device ID from **My device** and share it over an independent trusted channel. For Bluetooth + P2P, select the discovered Wi-Fi P2P service to establish the bridge before confirming the pairing. QR transport and cross-device validation remain open.

The initiating desktop can use Cancel pairing request to stop waiting before or after the confirmation code appears. If both devices already approved, check Trusted peers for a saved key. Use Decline for an incoming request. The receiver continues reading after the initiator approves so it can remove the pending request on disconnect while local consent is still pending.
